# Релизный cadence, changelog «для пользователя» и handoff CMO (growth)

Канон по механике тега и файлов: [RELEASE.md](RELEASE.md) и корневой [CHANGELOG.md](../CHANGELOG.md). Этот документ — **ритм**, **человеческие формулировки** в changelog и **связка с маркетингом** (Paperclip + каналы CMO).

Англоязычный growth-контекст: [MARKETING_LANDING_AND_GROWTH.md](MARKETING_LANDING_AND_GROWTH.md), чеклист: [GITHUB_GROWTH_CHECKLIST.md](GITHUB_GROWTH_CHECKLIST.md). Родительский план: [XDE-53#document-plan](/XDE/issues/XDE-53#document-plan) (Paperclip).

## 1. Semver и ритм релизов

Версия: **`MAJOR.MINOR.PATCH`**, теги **`vMAJOR.MINOR.PATCH`**, одна версия в `VERSION`, `package.json` и `cmd/skillget/main.go` — как в [RELEASE.md](RELEASE.md).

| Тип | Когда выпускать | Примеры |
|-----|------------------|---------|
| **PATCH** | Исправления, без изменения контракта для пользователя; мелкие правки docs/сообщений об ошибках | багфиксы CLI, подсказки, совместимые правки README |
| **MINOR** | Новые команды/флаги, новые возможности **без** ломающих изменений для существующих сценариев | новая подкоманда, улучшенный `search`, необязательные env |
| **MAJOR** | Ломающее изменение контракта CLI, путей, lockfile, env по умолчанию или требований к registry | переименование команд, смена формата lock, удаление флагов |

**Cadence (стартовый договор для org getskillpack):**

- **PATCH** — по мере накопления фиксов: целиться в **не реже 1 раза в 2 недели**, если есть хотя бы один пользовательски заметный фикс; иначе можно сдвинуть, но не копить «тихие» фиксы дольше месяца без тега.
- **MINOR** — когда есть **готовая** пользовательская ценность (не «почти»): ориентир **каждые 2–4 недели** в активной фазе; если фича крупная — один MINOR с понятным заголовком в release notes.
- **MAJOR** — редко, только после явного решения мейнтейнеров и текста миграции в changelog + GitHub Release (шаблон B в [RELEASE.md](RELEASE.md)).

Pre-release (`v0.x`): MINOR может включать **эпизодические** ломания до объявления `v1.0.0`; всё равно документируй в changelog как **Breaking** и поднимай MINOR (или MAJOR при подготовке к `1.0`).

## 2. «Значимый» релиз для growth

Считаем релиз **значимым для growth**, если выполняется **хотя бы одно**:

- MINOR или MAJOR (не patch-only), **или**
- PATCH с **видимым** эффектом для установки/CI (например починили критичный путь `install`, registry URL, lockfile), **или**
- Релиз сопровождается **новым** публичным гайдом/README-блоком, на который опирается маркетинг.

Для **patch-only** без пользовательского сюрприза: GitHub Release + строки в `CHANGELOG.md` достаточно; **отдельный handoff CMO не обязателен** (можно одной строкой в weekly-срезе CMO).

## 3. Шаблон блока в CHANGELOG.md — «что изменилось для пользователя»

Структура файла остаётся [Keep a Changelog](https://keepachangelog.com/). Под каждую версию добавляй краткий блок **для людей**, затем стандартные `Added` / `Changed` / `Fixed` / `Breaking` при необходимости.

Скопируй и заполни:

```markdown
## [X.Y.Z] - YYYY-MM-DD

### Для пользователя (кратко)

- **Что нового:** … одна-две фразы простым языком (RU).
- **Кому важно:** … (авторы skills, CI, локальная установка, …).
- **Действия:** … (ничего / обновить CLI / задать env / пересобрать lock).

### For users (short)

- **What’s new:** … one or two plain English sentences.
- **Who cares:** …
- **Action:** … (none / upgrade CLI / set env / refresh lock).

### Added
…

### Changed
…

### Fixed
…
```

Правило: блок **«Для пользователя»** не дублирует дословно каждый пункт ниже — он отвечает на вопросы «зачем мне обновляться» и «что сломается».

## 4. Handoff CMO после значимого релиза (Paperclip)

После **тега**, **GitHub Release** (шаблон из [RELEASE.md](RELEASE.md)) и обновлённого **CHANGELOG.md**:

1. В тикете growth-эпика или в дочерней задаче на канал (например X/Twitter cadence — [XDE-58](/XDE/issues/XDE-58), первая статья Dev.to — [XDE-57](/XDE/issues/XDE-57)) оставь **один** комментарий с фактами для поста — без лишних @-упоминаний, если политика board запрещает лишние heartbeat; **назначение на CMO** по согласованному тикету предпочтительнее, чем голый @ в тексте.
2. Скопируй шаблон ниже и подставь ссылки на **репозиторий**, **релиз**, **ключевые строки** из секции «Для пользователя».

Шаблон комментария (markdown):

```markdown
## Релиз для growth-handoff

- **Репозиторий / тег:** …
- **GitHub Release:** … (URL)
- **Одна фраза для соцсетей (EN):** …
- **Одна фраза (RU, опционально):** …
- **Аудитория:** …
- **Риски / честные оговорки:** … (или «нет»)

**Прошу CMO:** короткий пост в X + при накоплении материала — заявка на Dev.to по [плану XDE-53](/XDE/issues/XDE-53#document-plan).
```

Если нужен **явный запрос ручного шага board** (доступы, секреты, публикация вне репо) — по канону компании заведи отдельный тикет с назначением на board user с чеклистом, а не только этот комментарий.
